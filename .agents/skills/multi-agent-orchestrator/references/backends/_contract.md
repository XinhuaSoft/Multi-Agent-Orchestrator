# オーケストレーションバックエンド・アダプタ契約（`_contract.md`）

本ドキュメントは、`multi-agent-orchestrator` スキルのコアプロトコル（[../../SKILL.md](../../SKILL.md)）と具体的なオーケストレーションバックエンド実装（[orca.md](./orca.md)、[herdr.md](./herdr.md)、および将来的な追加バックエンド）を疎結合につなぐための**アダプタ契約**を定義します。

新しいバックエンドを追加する場合でも、本契約を満たすアダプタ文書を作成すれば、`SKILL.md` のコア手順を変更せずに利用できます。

---

## 1. アダプタ・メタデータチェックリスト

各バックエンドアダプタ文書（`references/backends/<backend_id>.md`）は、冒頭に以下のメタデータと事前条件を必ず記載してください。

| 項目 | 記載内容 |
|---|---|
| **Backend ID** | スキル起動時の `backend` パラメータに指定する識別子（例: `orca`, `herdr`） |
| **CLI / 接続先の解決** | 実行コマンド・環境変数・API エンドポイントの解決ルール（例: 環境変数優先 → `PATH` 検索） |
| **事前条件・起動手順** | デーモン／アプリの起動確認、バージョン確認、必要に応じたバージョン一致ドキュメントの取得手順 |
| **対応ケイパビリティ表** | 下記項目ごとの対応状況（ネイティブ対応 / アダプタ側エミュレーション / 非対応） |

### 対応ケイパビリティ確認項目
- [ ] Run / Task DAG のネイティブ管理（非対応時はローカル管理ファイル等の代替手順を明記）
- [ ] イベント駆動 wake またはポーリング待機（`wait_strategy` で詳細規定）
- [ ] ワークスペース分離（git worktree / clone / コンテナ / 共有のみ）
- [ ] 同一 Task への再試行リンク（`retry_of` 相当）と試行回数トラッキング
- [ ] エージェント種別・モデル・エフォート指定フラグ
- [ ] 双方向メッセージング（指示送信・質問受信・回答返信・承認プロンプト）
- [ ] ワーカー状態・出力の検証（`worker_inspect` の粒度と liveness 判定根拠）
- [ ] 司令塔セッション再起動後の Run 再接続（永続化）
- [ ] `context-guard` との連携可否

## 2. 10 個の抽象操作の契約

すべてのバックエンドアダプタは、以下の 10 個の抽象操作を具体的なコマンド／API／手順へマッピングして定義しなければなりません。バックエンドがネイティブ機能を持たない操作については、代替手段（エミュレーション）または制約事項を明示します。

| # | 抽象操作 | 役割 | 必須／主要入力（Inputs） | 期待される出力（Outputs） | 保証・契約（Guarantees） |
|---|---|---|---|---|---|
| 1 | `run_create` | Run 作成 | `objective`（確定済み目標）, 任意で `workspace_root`・メタデータ | `run_id`, Run のルートパスまたは識別子 | Run 単位で Task・ワーカー・イベントが紐づき、後続操作で参照可能になること |
| 2 | `task_create` | DAG 依存付き Task 作成 | `run_id`, `spec`（自己完結した指示）, `deps`（先行 `task_id` 配列、省略時は空） | `task_id`, 初期ステータス | `deps` の全 Task が完了するまで `task_list_ready` に現れない DAG 制約を保持すること |
| 3 | `task_list_ready` | 実行可能な Task 取得 | `run_id` | 依存解消済みかつ未着手の `task_id` と概要の一覧 | まだ着手可能でない依存待ち Task や完了済み Task を誤って返さないこと |
| 4 | `worker_start` | 新規・後任ワーカー起動 | `task_id`, `isolation`（`isolated` / `shared` + 任意名）, `worker_model`（`agent`, `model`, `effort`）, 再試行時は `retry_of`（前任識別子） | `dispatch_id`（または `worker_id`）, 作業パス, 起動ステータス | 起動したワーカーに Task spec が渡され、再試行時は新 Task を作らず同一 `task_id` に紐づくこと |
| 5 | `worker_send` | 指示・修正の送信 | 宛先 `dispatch_id`, `subject`, `body` | 送信確認（メッセージ ID または成否） | 稼働中ワーカーの受信経路へ安全に届き、ターミナルへの生入力を行わずに追加指示できること |
| 6 | `worker_reply` | 質問への回答 | `message_id`（質問イベント ID）, `body`（回答内容） | 返信確認 | 質問で待機中のワーカーへ回答が紐づき、ワーカーが作業を再開できること |
| 7 | `inbox_check` | イベント・通知の取得 | `run_id`（または司令塔識別子）, 取得上限・カーソル | 正規化イベント一覧（`worker_done` / `question` / `escalation` / `approval` 等） | 未処理のワーカー完了・質問・異常終了・承認要求を漏れなく取得できること |
| 8 | `worker_inspect` | 状態確認・出力参照 | `dispatch_id`（個別詳細）または `run_id`（一覧）, 出力取得上限 | ステータス、liveness 判定、終了理由、直近ログ／出力、作業パス | 「本当に停止したか／稼働中か／判定不能か」を判断できる一次証拠を返すこと |
| 9 | `worker_stop` | 停止 | `dispatch_id`, 任意で理由・クリーンアップ指定 | 停止結果（停止完了または現在状態） | 指定ワーカーのみを対象に安全に停止し、意図せず他のワーカーや成果物を破壊しないこと |
| 10 | `wait_strategy` | 待機・イベント受信方式 | 稼働中ワーカー一覧・未処理タスク有無 | 次サイクルの起動トリガー（到着イベントまたはポーリング結果） | バックエンドの設計に反する負荷・競合・二重起動を起こさずに次イベントを受け取ること |

## 3. 通信および待機セマンティクス

アダプタ文書は、バックエンドの通信モデルと待機規律を明確に定義してください。

### 3.1 待機モデル（`wait_strategy`）
- **イベント駆動型（Push / Turn-ending）**:
  - 実行すべき操作が終わったら司令塔はターンを終了し、バックエンドからの wake 通知で再開する。
  - 独自ポーリングループや監視スクリプトの禁止、直接ターミナル操作の禁止など、バックエンド固有の禁止事項を明記する。
- **ポーリング／ブロッキング待機型（Pull / Wait）**:
  - イベント駆動 wake が存在しないバックエンドでは、推奨待機コマンド・ポーリング間隔・バックオフ上限・タイムアウト時の振る舞いを定義する。
  - 待機タイムアウトだけではワーカー停止とみなさない（第 6 節参照）。

### 3.2 イベント型の正規化マッピング
バックエンド固有の通知・メッセージ形式を、コアプロトコルが扱う以下の 4 種類へ対応づけます。

| 正規化イベント | 意味 | 必須フィールド | 司令塔の基本アクション |
|---|---|---|---|
| `worker_done` | ワーカーのタスク完了・失敗報告 | `task_id`, `dispatch_id`, `outcome`（`succeeded` / `failed`）, 要約, 成果物／証拠 | 証拠を検証し、成功なら依存解除、失敗なら再試行（上限 3 回） |
| `question`（`ask`） | ワーカーからの判断依頼・質問 | `message_id`, `dispatch_id`, 質問本文 | 司令塔で回答可能なら `worker_reply`、ユーザー専権事項ならユーザーへ確認 |
| `escalation` | ブロッカー、異常停止、クラッシュ、`context-guard` 80% 通知 | `dispatch_id`, 理由（`exited` / `lost` / `blocked` 等）, 詳細 | `worker_inspect` で証拠確認の上、指示・引き継ぎ・ユーザー報告を実施 |
| `approval` | 人が許可すべき承認プロンプト | `dispatch_id`, 承認対象操作の詳細 | 自動承認せず、他作業を進めつつユーザーへ承認依頼 |

## 4. ワークスペース分離とファイル競合回避

アダプタ文書は、`worker_start` の `isolation` 指定がバックエンド上でどう実現されるかを明記してください。

- **分離モード（`isolated`）**:
  - 同一ファイル群を編集する複数ワーカーを並列起動する際の分離手法（例: git worktree の自動作成、独立ブランチ、一時クローン、コンテナ）と命名規則を定義する。
  - バックエンドがワークスペース作成を担う場合は、司令塔が手動でチェックアウトや worktree 作成を行わないルールを明記する。
  - リモート実行環境（SSH / WSL 等）に対応する場合は、配置オプションと制約を記載する。
- **共有モード（`shared`）**:
  - 単一ワーカー作業や、Git を使わない執筆・調査タスクで共有ワークスペースを使う際の指定方法を定義する。
  - 共有モードで並列実行する場合は、バックエンドによらず**ワーカーごとの担当ファイル排他分割**（編集許可ファイル／編集禁止ファイルの明記）を必須とする。
- **統合時の回収手順**:
  - 分離ワークスペースで生成された変更を統合する手順（マージ・パッチ適用・成果物収集）と、競合発生時の扱いを記載する。

## 5. モデル・エフォート指定のマッピング

コアプロトコルおよび [../model-routing.md](../model-routing.md) で解決された `(agent, model, effort)` を、バックエンドの起動引数へ変換する仕様を定義します。

1. **引数マッピング**: `agent`・`model`・`effort` がバックエンドのどのオプション／設定キーに対応するかを記載する。
2. **バージョン照合手順**: 実行中のバックエンドバージョンが受け付ける正確なモデル名・フラグ形式を確認するコマンド（例: `<cli> worker-start --help`）を明記する。
3. **非対応パラメータの劣化ルール（Graceful Degradation）**:
   - `effort` など一部パラメータをバックエンドがサポートしない場合の扱い（無視して警告ログを出す／プロンプト内へ方針として補完する等）を明記する。
   - **PII 安全モデルの保護**: 個人情報タスク向けに指定された安全なモデル・エージェントをバックエンドが起動できない場合、暗黙に別モデルへフォールバックしてはならず、起動を中止してユーザーへエスカレーションする。
4. **後任継承の保証**: `retry_of` による後任起動時にも、元タスクの `(agent, model, effort)` を同じマッピング規則で渡す。

## 6. 復旧・生存確認・安全性のマッピング

バックエンド固有のステータス表現を、コアプロトコルの安全規則へ正確に対応づけます。

### 6.1 生存確認（Liveness）と停止の証拠
- `worker_inspect` が返すステータスを以下の 3 区分へ分類して記載する:
  1. **稼働中（alive）**: 継続待機する状態
  2. **確証ある停止（verified_stopped）**: プロセス終了コード・停止理由（`exited` / `stopped` / `lost` 等）が確認できた状態 → 引き継ぎ・再試行の判断対象
  3. **判定不能（`unverifiable` / 沈黙 / タイムアウト）**: 停止の証拠にはならない状態 → 追加確認またはユーザー相談が必要
- 沈黙・タイムアウト・`unverifiable` のみで `worker_stop`・放棄・再試行を実行しないための具体的確認手順を明記する。

### 6.2 再試行とサーキットブレーカー
- 同一 `task_id` に対する再試行の指定方法（`retry_of` 相当）と、失敗回数（試行回数）の確認方法を記載する。
- バックエンドに自動サーキットブレーカーがある場合はその閾値と解除方法を、ない場合は司令塔側で「同一 Task 3 回失敗で自動再試行停止 → ユーザー報告」を強制する手順を記載する。

### 6.3 終了処理・クリーンアップ・保持（Teardown / Keep-open）
- `worker_stop`、Run 終了、およびワーカー完了時に、ワークスペース・ターミナル・ログが自動破棄されるか保持されるかを明記する。
- ユーザーが開いたまま残したい環境・ターミナル・成果物を誤って破棄しないためのオプション（keep-open 相当）を記載する。
- キャンセル・放棄・Task の再オープンはユーザー明示依頼時のみ行う操作として明確に区分する。

### 6.4 司令塔セッションの復元
- 司令塔自身のコンテキストが尽きて新セッションへ引き継ぐ際、既存 `run_id` へ再接続して `inbox_check` と `worker_inspect` で全状態を復元する手順を記載する。

## 7. 新しいバックエンド（例：`herdr`）を追加する手順

将来的に新しいオーケストレーションバックエンド（例: `herdr`）を追加する場合は、以下の手順で実装します。`SKILL.md` のコア手順（Step 0 のロジックや 8 ステップサイクル）を書き換える必要はありません。

1. **アダプタファイルの作成**:
   - `references/backends/herdr.md` を新規作成する。
   - 本契約（`_contract.md`）の第 1 節〜第 6 節をすべて網羅し、10 個の抽象操作・待機モデル・分離方針・モデルマッピング・生存確認とクリーンアップ手順を具体化する。
2. **サポート一覧への登録**:
   - [../../SKILL.md](../../SKILL.md) の「リファレンス一覧」に `./references/backends/herdr.md` を追記する。
   - 同ファイルの「Step 0: 2. オーケストレーション＆通信バックエンドの解決」にある「現在サポートしているバックエンド」一覧へ `herdr` を追加する。
3. **周辺リファレンスとの整合性確認**:
   - [../model-routing.md](../model-routing.md): 既定プリセットの `(agent, model, effort)` が `herdr.md` で解決可能か確認する。
   - [../task-spec-template.md](../task-spec-template.md): ワーカー側からの完了報告・質問コマンドの説明がバックエンド間で矛盾しないか確認する。
   - [../context-guard.md](../context-guard.md): `herdr` 経由で起動されるワーカーに `context-guard` が適用可能か（または第 2 段 `HANDOFF.md` 駆動のみか）を明記する。
4. **疎通検証**:
   - 最小の 2 タスク DAG（依存あり・並列あり）で `run_create`〜`worker_start`〜`inbox_check`〜`worker_inspect`〜最終報告まで通し検証し、未対応挙動があればアダプタ文書へ制約として記録する。
