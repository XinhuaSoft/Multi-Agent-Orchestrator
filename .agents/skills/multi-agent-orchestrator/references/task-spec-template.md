# Task Spec & HANDOFF.md テンプレート

このリファレンスは、司令塔がワーカーへ渡す**自己完結した Task spec** の作成要件と、コンテキスト枯渇やセッション切替に備える **`HANDOFF.md`** の運用テンプレートを定義する。

> **大前提**: ワーカーは司令塔と会話履歴・前提知識を共有していない。Task spec 単体（および引き継ぎ時の `HANDOFF.md`）だけで迷わず着手・検証・完了報告できる内容にすること。

---

## 1. 自己完結した Task spec の必須要件チェックリスト

ワーカーを起動する前に、Task spec に以下の要素がすべて含まれていることを確認する。

- [ ] **対象と行う変更**: 対象リポジトリ・ディレクトリ・ファイル・実行環境と、具体的に何を作成／変更／調査するか
- [ ] **作業種別と「完了の証拠」の定義**:
  - **コーディング系**: どのテスト・ビルド・リント・動作確認コマンドの出力をもって完了とするか
  - **執筆系**: 成果物ファイルの場所と形式、要件（構成・分量・トーン・必須要素）との適合および校正結果をどう示すか
  - **調査系**: 主張ごとの出典（URL と参照箇所）の記録方法と、確認できなかった事項を「未確認」と明記するルール
  - **複合系**: サブ作業ごとに種別を分け、それぞれの完了の証拠を明記
- [ ] **制約とファイル境界**:
  - **編集してよいファイル／ディレクトリ**と**触ってはいけないファイル／ディレクトリ**を明示する
  - コード以外の作業（執筆・調査など）や同一ワークスペースを共有する並列作業では、競合を防ぐためワーカーごとに担当ファイルを明確に分割する（例：執筆なら章ごと、調査ならテーマごとのメモファイル。最終統合は 1 人のワーカーが担当）
  - 禁止事項（破壊的操作の禁止、外部送信禁止、無断の仕様変更禁止など）と、使ってよいコマンド／ツール
- [ ] **非ゼロ終了コードの意味**:
  - コマンドの非ゼロ終了コードが「タスク失敗」を意味するのか、あるいは「エラー出力や診断結果の記録そのものが成果物」なのかを明記する
- [ ] **ワーカーの動作規則**:
  1. 最初に Task spec と `HANDOFF.md`（存在する場合）を読み、やるべきことを 1 つに絞って実行する
  2. 実行後は作業種別に応じた検証方法で結果を確認し、失敗なら原因を修正してやり直す
  3. **作業の区切りごとに `<自分のワークスペース>/HANDOFF.md` を更新する**
  4. 完了したら、成果物と完了の証拠を添えて完了報告を送る
  5. 行き詰まったら同じ方法での再試行は 3 回までとし、解決しなければ黙って停止せず司令塔へ質問を送って待機する
- [ ] **`context-guard` 未導入エージェント向けの保険文言**（該当時は必須）:
  - 「コンテキストが尽きそうだと感じたら作業を続けず、それまでの経過と残作業を `HANDOFF.md` に更新して終了報告せよ」を明記する（詳細は `./context-guard.md` を参照）
- [ ] **後任ワーカー用プレフィックス**（引き継ぎ・再試行時のみ）:
  - Task spec の先頭に「まず `HANDOFF.md` を読んで状況を復元せよ」を明記し、前任からの引き継ぎ情報を添える

## 2. 通常タスク用 Task spec テンプレート

そのままコピーし、`<...>` を埋めて使用する。通信コマンドや完了報告の具体的な書式は、使用中バックエンドのアダプターに従う。

```markdown
## 目的・概要
<このタスクで達成したいことを 1〜3 文で簡潔に記載>

## 対象と行う変更
- 対象ワークスペース / リポジトリ / 環境: <パスや環境情報>
- 対象ファイル / 対象範囲: <具体的なファイルパスや調査対象>
- 実施内容:
  1. <作業項目 1>
  2. <作業項目 2>
  3. <作業項目 3>

## 作業種別と完了の証拠
- 作業種別: <コーディング / 執筆 / 調査 / 複合>
- 完了の証拠（以下を満たし、完了報告に含めること）:
  - <例（コーディング）: `npm test` と `npm run lint` が終了コード 0 で通過し、実行コマンドと要約結果を報告する>
  - <例（執筆）: 指定パスへ出力し、構成・分量・トーン・必須項目のチェック結果を報告する>
  - <例（調査）: 主張ごとの出典 URL と参照箇所の対応表を作成し、根拠のない主張は「未確認」と明記する>

## 制約
- 編集してよいファイル:
  - <絶対パスまたはワークスペース相対パスを列挙>
- 触ってはいけないファイル:
  - <編集禁止のファイル・ディレクトリを列挙>
- 禁止事項:
  - <例: 破壊的コマンドの実行、未承認の依存追加、担当外ファイルの変更、個人情報の外部出力>
- 使ってよいコマンド / リソース:
  - <許可するツール・コマンド・参照先>
- 非ゼロ終了コードの扱い:
  - <「非ゼロ終了はタスク失敗とみなす」または「再現・検証ログの記録が成果物であり、非ゼロ終了時は出力を記録して報告する」を明記>

## 動作規則
1. 最初にこの Task spec と `<自分のワークスペース>/HANDOFF.md`（存在する場合）を読み、やるべきことを 1 つに絞って順に実行すること。
2. 実行後、上記の「作業種別と完了の証拠」に従って結果を検証すること。失敗した場合は原因を特定・修正して再検証すること。
3. 作業の区切りごとに `<自分のワークスペース>/HANDOFF.md` を更新し、進捗・証拠・残作業・落とし穴を最新に保つこと。
4. 完了したら、バックエンド既定の完了報告手段で「行ったこと・確認した証拠・残事項（なければなし）」を報告すること。失敗や未完了がある場合は成功と偽装せず正直に報告すること。
5. 行き詰まった場合は同じ方法での再試行を 3 回までとし、それでも解決しない場合は黙って停止せず、司令塔へ質問を送って待機すること。

## コンテキスト枯渇時のルール（※ context-guard 未導入時は必ず残す）
- コンテキストが尽きそうだと感じたら作業を続けず、それまでの成果・現在地・残作業・引き継ぎ事項を `<自分のワークスペース>/HANDOFF.md` に更新し、未完了である旨を明記して終了報告すること。
```

## 3. 後任引き継ぎ用 Task spec 追記テンプレート

前任ワーカーがコンテキスト枯渇・異常終了・停止などで交代する場合、**元の Task spec の先頭**に以下のブロックを追記して後任ワーカーを起動する。

```markdown
## 【最優先・後任ワーカー向け引き継ぎ指示】
あなたは前任ワーカーの後任である。**作業を始める前に、まず `<自分のワークスペース>/HANDOFF.md` を読んで状況を完全に復元せよ。**

- 引き継ぎ元: <前任ワーカーの識別子 / 試行回数>
- 交代理由: <例: コンテキスト使用量 80% 超過によるクリーン終了 / 異常終了>
- 参照すべき HANDOFF.md: `<自分のワークスペース>/HANDOFF.md`
- 前任までに確認済みの成果物・状態:
  - <既に完了・検証済みのファイルや変更点（やり直し不要な範囲）>
- 残っている作業（ここから再開すること）:
  - <未完了の作業項目>
- 司令塔からの補足・注意点:
  - <前任の HANDOFF.md が古い／空だった場合は、司令塔が成果物とログから再構築した現状サマリをここに記入する>
  - <同じ失敗を繰り返さないための制約・決定事項>

---
（以下に元の Task spec をそのまま続ける）
```

### 引き継ぎ時の補足ルール（司令塔向け）

- 前任の `HANDOFF.md` が古い・空の場合は、前任がまだ応答可能であれば追加メッセージで「現状を `HANDOFF.md` にまとめて報告せよ」と依頼してから後任を起動する。
- 前任がすでに応答不可であれば、ワークスペースの成果物ファイルとワーカーの直近ログから司令塔が状況を再構築し、上記テンプレートの「司令塔からの補足・注意点」へ書き込んでから後任を起動する。
- 後任ワーカーの `(agent, model, effort)` は、`./model-routing.md` の継続性ルールに従って前任と同一構成を維持する。

## 4. HANDOFF.md の配置とテンプレート

### 配置場所

| 役割 | 配置パス | 記載する視点 |
|---|---|---|
| **司令塔（主セッション）** | `<Run のルート>/HANDOFF.md` | コーディネーター視点の全体状況（Run 全体・DAG・全ワーカー・決定事項） |
| **各ワーカー** | `<自分のワークスペース>/HANDOFF.md` | 担当タスク単位の状況（対象ファイル・検証結果・残手順・落とし穴） |

### 必須記載事項（6 項目）

1. **目標と現在地**: 全体（または担当タスク）のどの段階にいるか
2. **完了したこと＋証拠**: 完了した作業と、それを裏付ける証拠（実行コマンドと結果要約、出典 URL と参照箇所、要件チェック結果など）
3. **進行中のこと**: 現在着手中のタスク ID・実行／ディスパッチ識別子・ブランチ・担当ファイル
4. **未着手・残タスク**: 優先順位付きの残作業リスト
5. **重要な発見・決定事項・落とし穴**: 後続や後任が同じ失敗を繰り返さないための知見・制約・合意事項
6. **次セッション／後任が最初に実行すべきコマンド**: 状況復元や作業再開のための最初の 1 手（コマンドまたは確認手順）

### 司令塔用 `<Run のルート>/HANDOFF.md` テンプレート

```markdown
# HANDOFF（司令塔）

最終更新: <YYYY-MM-DD HH:MM>

## 1. 目標と現在地
- Run ID / 作業名: <Run 識別子・名称>
- 目標: <ユーザーと合意した最終目標>
- 完了条件: <最終報告に必要な完了基準>
- 現在地: <例: 4 タスク中 2 タスク完了、1 タスク実行中、1 タスク待機中>
- 確定したモデル構成: <ロール別・タスク別の確定 (agent, model, effort)>

## 2. 完了したこと＋証拠
- [x] `<Task A>`: <概要> — 証拠: <テスト結果 / 成果物パス / 出典確認結果>
- [x] `<Task B>`: <概要> — 証拠: <結果要約>

## 3. 進行中のこと
- [ ] `<Task C>`（ワーカー: `<識別子>` / ロール: `<complex|clerical|simple|pii>` / ワークスペース・ブランチ: `<パス・ブランチ>` / 担当ファイル: `<ファイル一覧>`）
  - 状況: <最新の進捗・待機理由・context-guard 有無>

## 4. 未着手・残タスク（優先順位順）
1. `<Task D>`（依存: `<Task C>`）: <概要>
2. 最終統合・検証・ユーザーへの最終報告

## 5. 重要な発見・決定事項・落とし穴
- <ユーザーとの合意事項・方針変更>
- <PII 取り扱いや編集境界の注意点>
- <発生したエラーと回避策>

## 6. 次セッションが最初に実行すべきコマンド・手順
1. 使用中バックエンドの状態確認手段で、進行中タスクと未読メッセージ・ワーカー一覧を取得する
2. 成果物と各ワーカーの `HANDOFF.md` を確認し、次の調整・割り当てを再開する
```

> **主セッション自身の引き継ぎ**: 司令塔はイベント処理サイクルの記録フェーズごとに `<Run のルート>/HANDOFF.md` を最新に保つ。司令塔自身のコンテキストが尽きそうな場合は、ユーザーに「新しいセッションで本スキルと `<Run のルート>/HANDOFF.md` を読み込んで続行してください」と案内する。

### ワーカー用 `<自分のワークスペース>/HANDOFF.md` テンプレート

```markdown
# HANDOFF（ワーカー）

最終更新: <YYYY-MM-DD HH:MM>

## 1. 目標と現在地
- 担当タスク: <Task ID / タスク概要>
- 作業種別: <コーディング / 執筆 / 調査 / 複合>
- 現在地: <例: 全 4 ステップ中ステップ 2 まで完了、ステップ 3 の検証中>

## 2. 完了したこと＋証拠
- [x] <完了項目 1>
  - 証拠: <実行コマンドと結果要約 / 出力ファイルパス / 出典 URL と参照箇所>
- [x] <完了項目 2>
  - 証拠: <結果要約>

## 3. 進行中のこと
- 実行中の作業: <着手中の項目>
- 対象ブランチ / ワークスペース: <ブランチ名・パス>
- 変更中のファイル: <ファイルパス一覧>

## 4. 未着手・残タスク（優先順位順）
1. <次にやるべき作業>
2. <残りの作業>
3. 最終検証と完了報告

## 5. 重要な発見・決定事項・落とし穴
- <調査で判明した仕様・制約・根拠 URL>
- <失敗したアプローチと原因（後任が繰り返さないため）>

## 6. 後任が最初に実行すべきコマンド・手順
```bash
# 例: 現状の差分・ファイル・テスト状態を確認する
<最初に実行すべき確認コマンド>
```
- 次に着手する箇所: `<ファイルパス・行番号・セクション>`
```
